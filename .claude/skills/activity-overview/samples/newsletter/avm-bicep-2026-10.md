# Azure Verified Modules for Bicep — October 2026

October 2026 brought no new module, but it changed many existing ones. The Data Factory module no longer loses its Git repository configuration: version 0.13.0 replaced its eleven Git parameters with a single `gitConfiguration` object — a breaking change, described under [Breaking changes and deprecations](#breaking-changes-and-deprecations). Personal host pools can now use the `MultiplePersistent` load-balancer type, scheduled query rules accept the `SimpleLogAlert` kind, the SQL managed instance module lost a wrong storage ceiling, and a group of Azure Local and Arc modules moved to newer API versions. The Dev Test Lab module declared the deprecation of its `secret` child module.

The stories below follow every thread of the month by its state: 14 landed, 10 in flight, 11 stalled after activity in October 2026 and 3 closed as not planned by their author the same day; 20 quieter threads carried over are listed in one line each. Four open pull requests propose a new module; they are listed under [Coming up and stuck](#coming-up-and-stuck). Most of the merged work (49 of 64 classified pull requests) was plumbing — making the shared test pipeline and the test environment reliable — told theme by theme under [Plumbing: what was engineered](#plumbing-what-was-engineered). 12 people opened their first pull request or issue in the repository.

## Breaking changes and deprecations

**Declared by the maintainers**

**Landed — The scheduled query rule module now accepts the `SimpleLogAlert` kind, sending only the properties that kind supports**

On 14 September 2026 community contributor @balliere opened [issue #7345](https://github.com/Azure/bicep-registry-modules/issues/7345) against [`avm/res/insights/scheduled-query-rule`](https://github.com/Azure/bicep-registry-modules/tree/82950838e7cefc9a32e813055fbf407ea5819e15/avm/res/insights/scheduled-query-rule) version 0.6.0, a feature request saying "kind: 'SimpleLogAlert' is missing". The `kind` parameter only allowed `'LogAlert'` and `'LogToMetric'`. Three minutes later the same author opened [PR #7346](https://github.com/Azure/bicep-registry-modules/pull/7346) from a fork.

The [first commit](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/9342baa54912157f8108e6e412cbd5023597bbde) added `'SimpleLogAlert'` to the allowed values of `kind`; a [follow-up commit](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/c829f355bc16728effb6238eeb2476a01f927249) ("invert logic") made the block of `LogAlert`-only properties apply whenever `kind != 'LogToMetric'`. On 18 September 2026 an automation account (a coding agent), requested by @abhishekaryams, [objected](https://github.com/Azure/bicep-registry-modules/pull/7346#discussion_r4043964689) that this "can result in sending unsupported properties when kind is 'SimpleLogAlert'", and [asked](https://github.com/Azure/bicep-registry-modules/pull/7346#discussion_r4043964738) for an e2e test deploying the new kind. On 15 October 2026 @abhishekaryams [requested changes](https://github.com/Azure/bicep-registry-modules/pull/7346#pullrequestreview-5527550172), asking the author to check the automated review comments (from a coding agent) and to rebase the branch.

The rework followed the same day. [Commit 51d538b](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/51d538b1c0178053fb77c19c19225b422f563a6d) restored the condition `kind == 'LogAlert'` for the `LogAlert`-only block and added a separate `SimpleLogAlert` block carrying only `autoMitigate` / `resolveConfiguration`, plus a `simple-log-alert` e2e test. [Commit 768cc1f](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/768cc1f670bdcf9422ddaeb8ed37bd982dc8608a) also passed `severity`, because "The service requires severity for kind SimpleLogAlert". After a [further automated comment](https://github.com/Azure/bicep-registry-modules/pull/7346#discussion_r4280145980) that the `resolveConfiguration` path was untested, [commit da14db5](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/da14db5430299185677fcdaff94af5b465ebe4ea) added a `simple-log-alert-resolve` test. [Commit 9701dde](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/9701dde57771b0ecde9083668089c5539030ebe8) recorded a service constraint: "The service requires autoMitigate / resolveConfiguration.autoResolved to be false for SimpleLogAlert rules unless the criteria set minRecurrenceCount." The `ruleResolveConfiguration` description now reads "For kind SimpleLogAlert, autoResolved must be false unless the criteria specify a minRecurrenceCount."

Between the first review request on 14 September 2026 and the review on 15 October 2026 the author asked for review several times, and maintainer @AlexanderSehr [pinged](https://github.com/Azure/bicep-registry-modules/pull/7346#issuecomment-6067342399) the reviewer on 8 October 2026. On 21 October 2026 maintainer @jaredfholgate [approved](https://github.com/Azure/bicep-registry-modules/pull/7346#pullrequestreview-5600677486), [dismissed](https://github.com/Azure/bicep-registry-modules/pull/7346#event-33851283011) the earlier change request with the note "Reviewed myself", and merged. The checks on the [head commit](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/7f764679e393226eb85fae8b11db04ea00daeb1f) were passing (nine checks). All five review threads on the PR are marked resolved on GitHub, by @jaredfholgate, as gathered on 27 November 2026.

**What landed:** PR #7346 was merged on 21 October 2026 and released the same day as [0.6.1](https://github.com/Azure/bicep-registry-modules/tree/avm/res/insights/scheduled-query-rule/0.6.1) (`br/public:avm/res/insights/scheduled-query-rule:0.6.1`), with no breaking changes. The changelog says: "Added support for kind `SimpleLogAlert`. Only the `SimpleLogAlert`-supported properties (`severity`, `autoMitigate`, `resolveConfiguration`) are applied for this kind." and "Added `simple-log-alert` and `simple-log-alert-resolve` e2e tests." Issue #7345 was closed as completed on 21 October 2026. Nothing discussed was left out.

The PR also flags one behaviour change for existing users: a deployment that used `enabled: false` to remove capture settings will now keep them on the resource. ## Plumbing: what was engineered

### Shared pipeline utilities

Most of October 2026's plumbing work went into the shared machinery every module's test pipeline runs, not into modules: the PowerShell helpers and offline tests under `utilities/`, the GitHub Actions templates under `.github/actions/templates/` (module deployment validation, PSRule and Pester validation, environment setup) and the reusable workflows under `.github/workflows/`. Of the theme's 40 pull requests, 39 were opened by Jared Holgate (@jaredfholgate): 28 were merged between 1 and 23 October 2026, 10 were closed without merging and one, [#7521](https://github.com/Azure/bicep-registry-modules/pull/7521), is an open draft. The 40th, [#7032](https://github.com/Azure/bicep-registry-modules/pull/7032), is a module change opened by an automation account (a coding agent) that carries one test-pipeline commit (strand 4). Of the 28 merged PRs, ten were approved by @jtracey93 before merging; one ([#7525](https://github.com/Azure/bicep-registry-modules/pull/7525)) was reviewed only by an automation account; for the other 17 the record shows a review requested and none given. For all ten closed PRs the record states no reason for closing; for seven of them a commit with the same subject is part of a merged consolidation PR, and for two more a merged PR's commit message says it carries their subject matter, as given below. Many descriptions start from a specific failed CI job, linked to its run, and state that module files are untouched ("Tooling-only follow-up to the shared-CI failures in [automatic run 37701216720]", [#7487](https://github.com/Azure/bicep-registry-modules/pull/7487)). Apart from #7451, which published a module version, none of the merged PRs changed a module version. The work falls into five strands.

**1. Keeping module deployment tests from failing on transient Azure trouble (19 PRs).** A module's end-to-end test deploys real resources into a test subscription, and the descriptions document jobs that failed on regional capacity shortages, timeouts and unreadable errors rather than on the module.

*Readable failures.* [#7443](https://github.com/Azure/bicep-registry-modules/pull/7443) (merged 2 October 2026) notes that "the job printed `Template is not valid.` without the underlying reason" because the helper kept Azure's response only in `ErrorRecord.TargetObject`; it now attaches "readable Azure error codes, messages, targets and nested errors through `ErrorDetails`", while "Supplied parameter values, including secure strings and escaped values, are redacted."

*One retry budget across regions.* The core change is [#7455](https://github.com/Azure/bicep-registry-modules/pull/7455) (merged 3 October 2026), a coordinator that gives a test "at most **three distinct region candidates and three deployment attempts total**, rather than multiplying deployment retries by region". It moves an automatically selected test location only when the original deployment is "authoritatively `Failed`, every structured error is regional, and its partial resources and deployment records are confirmed removed"; pinned locations stay where they are. A later consolidation, [#7517](https://github.com/Azure/bicep-registry-modules/pull/7517) (merged 11 October 2026), "shares one four-hour status-recovery deadline across coordinated deployment attempts". The separate proposal for that deadline, [#7511](https://github.com/Azure/bicep-registry-modules/pull/7511) (closed unmerged; the record states no reason), explains it: a Log Analytics deployment hit a "genuine 100-second HttpClient timeout" and recovery "observed the same Running root until its one-hour window expired"; its commit, "fix(ci): share a four-hour deployment recovery deadline", is one of #7517's commits.

*Teaching the coordinator which Azure errors justify trying another region.* Most of the remaining PRs add one exact Azure error message to the classifier, each anchored to the selected region so that an unrelated error is not retried elsewhere:
- Machine Learning with Cosmos DB "regional high demand" ([#7465](https://github.com/Azure/bicep-registry-modules/pull/7465), closed unmerged; the record states no reason). Its classifier went into [#7464](https://github.com/Azure/bicep-registry-modules/pull/7464) (merged 6 October 2026, approved by @jtracey93), which calls itself "the consolidated tooling review": it includes "the Cosmos classifier from [#7465]", "the AKS classifier from [#7467]" (AKS preflight failures where the supported-zone set is empty) and "the complete twelve-file non-`avm/` slice from [#7374]", and adds a fix for missing nested child deployments during preflight cleanup.
- `LocationNotAvailableForResourceType`, recognised "only when its rejected location matches the selected resource region" ([#7486](https://github.com/Azure/bicep-registry-modules/pull/7486), merged 7 October 2026).
- Search SKU capacity (`ResourcesForSkuUnavailable`) and a second wording of a managed-environment capacity error ([#7487](https://github.com/Azure/bicep-registry-modules/pull/7487), merged 8 October 2026, approved by @jtracey93); its commit reports "10 expected red failures before the change, then 724 passed". The same PR lets setup "Reuse available PowerShell dependencies without Gallery access".
- Search `InsufficientResourcesAvailable` ("The region '<region>' is currently out of the resources required to provision new services.") in [#7509](https://github.com/Azure/bicep-registry-modules/pull/7509) (closed unmerged; the record states no reason); its commit "fix(ci): retry Search regional capacity exhaustion" is one of #7517's commits.

*Making the reads around a deployment tolerate failure.* [#7457](https://github.com/Azure/bicep-registry-modules/pull/7457) (merged 3 October 2026) stops parsing the display text of a deployment-operation error as JSON and reads the structured error instead ("Read ARM operation errors through the shared paginated scope reader instead of parsing SDK display text"). [#7470](https://github.com/Azure/bicep-registry-modules/pull/7470) (merged 6 October 2026, approved by @jtracey93) gives the region metadata reads `Get-AzResourceProvider` and `Get-AzLocation` "three total attempts each, with five-second delays". [#7478](https://github.com/Azure/bicep-registry-modules/pull/7478) (merged 7 October 2026, approved by @jtracey93) handles management-group deployments that Azure completed although the client reported HTTP 403, because "repeating the template with a new deployment name can create another set of resources"; it now observes the original deployment and returns its outputs "only for confirmed `Succeeded`". [#7492](https://github.com/Azure/bicep-registry-modules/pull/7492) (merged 9 October 2026, approved by @jtracey93) bounds cleanup and polling reads to "three total reads, five seconds apart", and its follow-up [#7500](https://github.com/Azure/bicep-registry-modules/pull/7500) (merged 9 October 2026, approved by @jtracey93) stops "replaying authorization-denied deployments". [#7479](https://github.com/Azure/bicep-registry-modules/pull/7479) (deployment deletions still in `Deleting`, and Graph operation metadata that an older API version omits) was closed unmerged; the record states no reason, and #7486's second commit says it carries "bounded deletion-response handling, Graph operation metadata, and cross-platform fixture isolation". [#7514](https://github.com/Azure/bicep-registry-modules/pull/7514) (recovering an Image Builder status read that failed with a connection reset) was closed unmerged; the record states no reason, and a commit with its subject and body is one of #7517's commits.

*Keeping the pipeline itself from tripping.* [#7446](https://github.com/Azure/bicep-registry-modules/pull/7446) (merged 2 October 2026) stops the deployment-matrix scope discovery from crashing on nested templates whose `properties.template` is an ARM expression, treating them "conservatively, like external template links". [#7445](https://github.com/Azure/bicep-registry-modules/pull/7445) (merged 2 October 2026) keeps `.Platform - Rerun failed workflows` away from the generic `.Module - Check and Publish` workflow, so "Only resource, pattern, and utility module workflows remain eligible."

*Consolidations.* Several fixes were proposed separately and then merged together.
