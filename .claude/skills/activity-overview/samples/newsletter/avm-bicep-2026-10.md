# Azure Verified Modules for Bicep — October 2026

October 2026 brought no new module, but it changed many existing ones. The Data Factory module no longer loses its Git repository configuration: version 0.13.0 replaced its eleven Git parameters with a single `gitConfiguration` object — a breaking change, described under [Breaking changes and deprecations](#breaking-changes-and-deprecations). Personal host pools can now use the `MultiplePersistent` load-balancer type, scheduled query rules accept the `SimpleLogAlert` kind, the SQL managed instance module lost a wrong storage ceiling, and a group of Azure Local and Arc modules moved to newer API versions. The Dev Test Lab module declared the deprecation of its `secret` child module.

The stories below follow every thread of the month by its state: 14 landed, 10 in flight, 11 stalled after activity in October 2026 and 3 closed as not planned by their author the same day; 20 quieter threads carried over are listed in one line each. Four open pull requests propose a new module; they are listed under [Coming up and stuck](#coming-up-and-stuck). Most of the merged work (49 of 64 classified pull requests) was plumbing — making the shared test pipeline and the test environment reliable — told theme by theme under [Plumbing: what was engineered](#plumbing-what-was-engineered). 12 people opened their first pull request or issue in the repository.

## Breaking changes and deprecations

**Declared by the maintainers**

- **[`avm/res/data-factory/factory`](https://github.com/Azure/bicep-registry-modules/tree/82950838e7cefc9a32e813055fbf407ea5819e15/avm/res/data-factory/factory) [0.13.0](https://github.com/Azure/bicep-registry-modules/tree/avm/res/data-factory/factory/0.13.0)** (the Data Factory module, `Microsoft.DataFactory/factories`; published on 14 October 2026): the eleven `git*` parameters, `gitConfigureLater` included, were removed in favour of one `gitConfiguration` object, and "`collaborationBranch` and `rootFolder` no longer default to `'main'` and `'/'`." **Landed — The scheduled query rule module now accepts the `SimpleLogAlert` kind, sending only the properties that kind supports**

On 14 September 2026 community contributor @balliere opened [issue #7345](https://github.com/Azure/bicep-registry-modules/issues/7345) against [`avm/res/insights/scheduled-query-rule`](https://github.com/Azure/bicep-registry-modules/tree/82950838e7cefc9a32e813055fbf407ea5819e15/avm/res/insights/scheduled-query-rule) version 0.6.0, a feature request saying "kind: 'SimpleLogAlert' is missing". The `kind` parameter only allowed `'LogAlert'` and `'LogToMetric'`. Three minutes later the same author opened [PR #7346](https://github.com/Azure/bicep-registry-modules/pull/7346) from a fork.

The [first commit](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/9342baa54912157f8108e6e412cbd5023597bbde) added `'SimpleLogAlert'` to the allowed values of `kind`; a [follow-up commit](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/c829f355bc16728effb6238eeb2476a01f927249) ("invert logic") made the block of `LogAlert`-only properties apply whenever `kind != 'LogToMetric'`. On 18 September 2026 an automation account (a coding agent), requested by @abhishekaryams, [objected](https://github.com/Azure/bicep-registry-modules/pull/7346#discussion_r4043964689) that this "can result in sending unsupported properties when kind is 'SimpleLogAlert'", and [asked](https://github.com/Azure/bicep-registry-modules/pull/7346#discussion_r4043964738) for an e2e test deploying the new kind. On 15 October 2026 @abhishekaryams [requested changes](https://github.com/Azure/bicep-registry-modules/pull/7346#pullrequestreview-5527550172), asking the author to check the automated review comments (from a coding agent) and to rebase the branch.

The rework followed the same day. [Commit 51d538b](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/51d538b1c0178053fb77c19c19225b422f563a6d) restored the condition `kind == 'LogAlert'` for the `LogAlert`-only block and added a separate `SimpleLogAlert` block carrying only `autoMitigate` / `resolveConfiguration`, plus a `simple-log-alert` e2e test. [Commit 768cc1f](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/768cc1f670bdcf9422ddaeb8ed37bd982dc8608a) also passed `severity`, because "The service requires severity for kind SimpleLogAlert". After a [further automated comment](https://github.com/Azure/bicep-registry-modules/pull/7346#discussion_r4280145980) that the `resolveConfiguration` path was untested, [commit da14db5](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/da14db5430299185677fcdaff94af5b465ebe4ea) added a `simple-log-alert-resolve` test. [Commit 9701dde](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/9701dde57771b0ecde9083668089c5539030ebe8) recorded a service constraint: "The service requires autoMitigate / resolveConfiguration.autoResolved to be false for SimpleLogAlert rules unless the criteria set minRecurrenceCount." The `ruleResolveConfiguration` description now reads "For kind SimpleLogAlert, autoResolved must be false unless the criteria specify a minRecurrenceCount."

Between the first review request on 14 September 2026 and the review on 15 October 2026 the author asked for review several times, and maintainer @AlexanderSehr [pinged](https://github.com/Azure/bicep-registry-modules/pull/7346#issuecomment-6067342399) the reviewer on 8 October 2026. On 21 October 2026 maintainer @jaredfholgate [approved](https://github.com/Azure/bicep-registry-modules/pull/7346#pullrequestreview-5600677486), [dismissed](https://github.com/Azure/bicep-registry-modules/pull/7346#event-33851283011) the earlier change request with the note "Reviewed myself", and merged. The checks on the [head commit](https://github.com/Azure/bicep-registry-modules/pull/7346/commits/7f764679e393226eb85fae8b11db04ea00daeb1f) were passing (nine checks). All five review threads on the PR are marked resolved on GitHub, by @jaredfholgate, as gathered on 27 November 2026.

**What landed:** PR #7346 was merged on 21 October 2026 and released the same day as [0.6.1](https://github.com/Azure/bicep-registry-modules/tree/avm/res/insights/scheduled-query-rule/0.6.1) (`br/public:avm/res/insights/scheduled-query-rule:0.6.1`), with no breaking changes. ### Other plumbing

Two small merged changes touched only modules' `metadata.json` files. [#7493](https://github.com/Azure/bicep-registry-modules/pull/7493) by maintainer Andy Jordan (@andyleejordan), merged 8 October 2026, fixes a typo carried in from #7349: the API Management `named-value` metadata had `canonicalType` set to `Microsoft.ApiManagement/service/namesValues`. Because "`Set-ModuleReadMe` reads `canonicalType` before falling back to the API specs lookup", the README generator rewrote the README header to the misspelled name, so the static test "Set-ModuleReadMe script should not apply any updates" failed "for any PR that touches API Management"; the author found it in #7472 and "pulled the fix out so it can land on its own". It is "a metadata-only change, so there's no version bump or CHANGELOG entry", and the record cannot tie a release of [`avm/res/api-management/service`](https://github.com/Azure/bicep-registry-modules/tree/82950838e7cefc9a32e813055fbf407ea5819e15/avm/res/api-management/service) to it. [#7471](https://github.com/Azure/bicep-registry-modules/pull/7471) by Arjen Huitema (@arjenhuitema), merged 6 October 2026, has no description; its single commit adds @arjenhuitema "as the owner for the Network Security Group and Azure SQL Server modules.", and the changed files are those two modules' `metadata.json`.
