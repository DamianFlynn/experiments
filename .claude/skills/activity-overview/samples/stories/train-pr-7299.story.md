**A new Function App pattern module (`avm/ptn/app/function-app`), released as 0.1.0 without private networking and with the Consumption plans kept.**

On 14 May 2026 a commit on the PR's branch changed the default of `appServicePlanSkuName` from `'Y1'` (Consumption) to `'FC1'` (Flex Consumption) (https://github.com/Azure/bicep-registry-modules/pull/7299/commits/ba0a412228bb31d1b99673174b0ad7ab1eed4385). On 25 August 2026 the commit "narrow v0.1 scope to the golden path" removed the `enableWafAlignment` switch and the `functionAppSubnetResourceId`, `privateEndpointSubnetResourceId` and `privateDnsZoneResourceIds` parameters from `main.bicep`; its message says the switch "promised more than an infrastructure module can guarantee", and the changelog line it added reads "Private networking is intentionally out of scope" (https://github.com/Azure/bicep-registry-modules/pull/7299/commits/6ed2229f215409dd6d75a463e3b99de2aa12aaf7). bwateratmsft opened #7299 the next day (https://github.com/Azure/bicep-registry-modules/pull/7299).

On 18 September 2026 AlexanderSehr asked why both `logAnalyticsWorkspaceName` and `logAnalyticsWorkspaceResourceId` existed (https://github.com/Azure/bicep-registry-modules/pull/7299#discussion_r4047195108). Within the hour a commit removed the `logAnalyticsWorkspaceName` parameter and the `existingLogAnalyticsWorkspace` reference (https://github.com/Azure/bicep-registry-modules/pull/7299/commits/3d3452ccd3ea017b9595f1d486df3551e25dbaa2), and the author replied "Agreed, no need for both." (https://github.com/Azure/bicep-registry-modules/pull/7299#discussion_r4047622536).

The same day the author reported that "the only part still failing is due to the storage account not having a firewall set up"; a firewall plus a virtual network would rule out the "Consumption (Classic)" plan (https://github.com/Azure/bicep-registry-modules/pull/7299#issuecomment-5732578246). On 21 September 2026 AlexanderSehr explained that the rule check applies to the `defaults` and `waf-aligned` tests and that, for a pattern module only, renaming the `defaults` test takes it out of that check (https://github.com/Azure/bicep-registry-modules/pull/7299#issuecomment-5758399260). The next commit renamed the test to `minimal` and touched only test files and the README (https://github.com/Azure/bicep-registry-modules/pull/7299/commits/9320acf62b43a6815ad70646b0a4cc98146a4838); the author wrote "All green now." (https://github.com/Azure/bicep-registry-modules/pull/7299#issuecomment-5762068160). No later commit added a firewall, network parameter or plan restriction to `main.bicep`. Nobody wrote that the firewall requirement was waived; the record shows the rename, then AlexanderSehr's further comments on test resource names (https://github.com/Azure/bicep-registry-modules/pull/7299#discussion_r4104266971), the fixed identifiers that answered them (https://github.com/Azure/bicep-registry-modules/pull/7299/commits/179ba533258443f30c9401c0e9f19ece6a74c5c8), and his approval.

**What landed.** AlexanderSehr approved #7299 on 29 September 2026 (https://github.com/Azure/bicep-registry-modules/pull/7299#pullrequestreview-5355888034) and it was merged that day, publishing version 0.1.0. Its changelog: "Supports Flex Consumption (the default), Consumption, Elastic Premium and Dedicated hosting plans." and "Applies HTTPS-only, TLS 1.2 minimum, disabled FTP/FTPS publishing and disabled anonymous blob access. Private networking is outside the module's scope." Check results and thread resolutions are not in this store.
